## 1. Problem statement

Departments build one-off tracking for each application. Data is fragmented, inconsistent, and hard to compare. The business wants one shared analytics tool, similar in spirit to Google Analytics, usable by all departments. Applications send data as **events over a messaging system**, with no HTTP ingestion API, so that no API rate limit caps how much data can be sent. The tool must be reusable: a future application integrates without any change to the analytics service.

## 3. Scope summary

In scope for v1: messaging-based ingestion; versioned event contract; reusable producer client kit (TypeScript, Node.js, Python); simulator producer applications built by this project as the O-1 samples; PII stripping at intake with a per-tenant pseudonymous user id; validation, deduplication and bounded dead-letter handling; refusal of unauthorised publishes; multi-tenant storage and query; web dashboard (aggregates only, small-cell suppression) for users; **admin screen** (MFA for admins) for accounts, tenants, entitlements, producer credentials, retention, ingestion health, dead-letter handling, GDPR requests and an audit log viewer; audit; local Docker and staging-like environments. Only deployment configuration remains file-based.
Out of scope: see Section 10.

## 5. User stories and acceptance criteria

Nominal load means 1,000 events/second (CR-009).

### US-1 (P-1, REQ-1, REQ-2, REQ-4)

As a producer-app developer, I want to publish events using the client kit, so that my application is tracked without calling an analytics API or hitting rate limits.

- AC-1.1: Given an onboarded producer with valid credentials, when it publishes a contract-valid event via the client kit (TypeScript, Node.js or Python) at nominal load (1,000 events/s), then the event is accepted by the messaging layer and becomes queryable in the dashboard within 10 seconds at p95 [confirmed].
- AC-1.2: Given a deployed environment, when a port scan and route inventory of all analytics-platform components is run, then no route accepts event payloads, and an HTTP POST of an event to any exposed service returns a 4xx response and stores nothing (CR-020).
- AC-1.3: Given a load test of 5,000 events/second sustained for 10 minutes [confirmed] from at least 3 simulator producers, when events are published, then 0 events are rejected for rate reasons and 100% of valid events are stored within 5 minutes after the load stops [proposed, Q-36].

### US-2 (P-1, P-3, REQ-5, REQ-14, REQ-22)

As a producer-app developer, I want to onboard a new application using configuration only, so that I do not need analytics-team code changes.

- AC-2.1: Given a new application not previously known, when a platform admin adds a tenant and a producer credential in the admin screen and the developer follows the published docs, then the first valid event from that app appears in the dashboard with no change to analytics-service source code, no contract release and no rebuild of its images.
- AC-2.2: Given the onboarding docs and client kit, when a fresh-context agent that has only the published docs and kit follows them in a timed trial, then the first event is visible in 60 minutes or less [confirmed, Q-7b; trial runner per CR-022].
- AC-2.3: Given the two simulator producer applications built by this project, when they run, then events from both are recorded in separate tenants (objective O-1).
- AC-2.4: Given the onboarding docs, when reviewed, then they state that each producer application must publish a privacy notice before sending events, and that PII must not be sent in allow-listed values (CR-004).
- AC-2.5: Given a clean machine with Docker, when the documented docker-compose command is run, then the full platform starts locally and passes a smoke test, and the staging-like Docker environment passes the same smoke test (REQ-22).

### US-3 (P-1, REQ-3)

As a producer-app developer, I want a versioned event contract, so that my integration keeps working as the platform evolves.

- AC-3.1: Given the contract, when it is published, then every event envelope carries a contract version and every event type has a machine-readable schema in the repository with a changelog.
- AC-3.2: Given a producer using contract version N, when the platform releases a backward-compatible version N+1, then the producer's events continue to be accepted and stored with 0 failures in a contract compatibility test run in CI, for each supported client kit language.
- AC-3.3: Given a breaking change to the contract, when it is proposed, then it is released only as a new major version, and the previous major version is supported for at least 6 months [confirmed].

### US-4 (P-1, REQ-8)

As a producer-app developer, I want events to survive analytics-side slowness or outages without breaking my application, so that tracking never impacts my users.

- AC-4.1: Given the analytics consumer side is stopped for 15 minutes [confirmed], when producers keep publishing at nominal load, then after restart 100% of events published during the outage are stored, and 0 are lost.
- AC-4.2: Given the messaging layer is unreachable, when the client kit publishes an event, then the host application call returns without throwing and without blocking for more than 50 ms at p99 [confirmed, Q-23], and the client kit buffers events up to a configured limit with a default of 10,000 events [proposed, Q-36].
- AC-4.3: Given the client kit buffer limit is reached during a prolonged outage, when further events are emitted, then the kit drops the oldest buffered events first [confirmed, Q-13], exposes a dropped-event counter, and logs one warning per interval without personal data.
- AC-4.4: Given a failure of the event store, when it is restored from backup, then the restore completes within 4 hours, at most 5 minutes of stored events are lost (the accepted loss window of NFR-7), and the deletion ledger is re-applied before queries are served (REQ-30) (CR-006).
- AC-4.5: Given one tenant publishing at 4 times the nominal rate of the other tenants, when the test runs for 10 minutes, then the other tenants' p95 ingest-to-queryable latency stays at or below 10 seconds (NFR-22) (CR-018).

### US-5 (P-2, REQ-10, REQ-11, REQ-25, REQ-28, REQ-29)

As a department dashboard user, I want an overview of an application's usage, so that I can understand what is happening.

- AC-5.1: Given an authenticated user entitled to application A with stored events, when they open the overview for a date range, then total events, unique users (distinct pseudonymous ids), an events-over-time series and the top 10 event types are shown, and event totals equal a direct count of stored events by event time in that UTC range (tolerance 0).
- AC-5.2: Given a 30-day range on a dataset of 10 million events [confirmed], when the overview loads, then it renders within 2 seconds at p95 [confirmed].
- AC-5.3: Given an entitled application with no events in the range, when the overview loads, then an empty-state message is shown instead of an error, and no error is logged.
- AC-5.4: Given a user with role "user", when they use any dashboard screen or call any query endpoint, then every response contains aggregates only: no per-user records, no raw user id and no pseudonymous id (confirmed, Q-25).
- AC-5.5: Given events with event times 23:59:59 UTC and 00:00:00 UTC on consecutive days and a late-arriving event (ingested after its UTC day ended), when the daily series is shown, then each event falls in the UTC day of its event time and the late event appears in its event-time day (CR-008).
- AC-5.6: Given a filter (for example country, browser/OS family, event type, short date range) that matches fewer than 5 unique users, when the dashboard renders, then the cell shows a suppressed marker and not the number, and totals shown elsewhere do not reveal the suppressed value by subtraction in the same view (CR-015).

### US-6 (P-2, REQ-12)

As a department dashboard user, I want to filter by application, date range and event type, so that I can answer specific questions.

- AC-6.1: Given the overview, when the user selects an application, a date range and an event type, then all figures reflect exactly that filter and the active filters are visible and can be cleared.
- AC-6.2: Given a selected range, when the user enables comparison with the previous period, then both periods are shown with percentage change, and an invalid range (end before start, or longer than 13 months [confirmed]) shows a validation message and does not run the query.

### US-7 (P-2, REQ-9, REQ-13)

As a department dashboard user, I want to see only data for applications I am entitled to, so that data stays separated between departments.

- AC-7.1: Given user U entitled to tenant A only, when U requests data for tenant B (via UI or by calling the query API directly with tenant B's id), then the response is 403 or 404 and contains no tenant B data.
- AC-7.2: Given an automated isolation test suite with at least 2 tenants, seeded events and the same event ids used in both tenants, when run in CI, then 0 cross-tenant records appear in any query, neither tenant's events are suppressed or altered by the other's duplicate ids, and a user with no entitlements sees an empty application list.

### US-8 (P-2, P-3, REQ-13, REQ-27)

As a dashboard user or admin, I want to sign in with my platform account, so that only authorised staff see analytics.

- AC-8.4: Given an admin account, when the admin signs in with a correct password but without a valid TOTP code, then they cannot reach the admin screen or any admin function and an audit entry is written; with a valid TOTP code they reach it (confirmed, CR-005).

### US-10 (P-3, REQ-15, REQ-21)

### US-11 (P-3, P-4, REQ-18, REQ-23, REQ-20, REQ-30)

- AC-11.1: Given a request whose requester identity was verified by the documented process outside the system (the admin records the verification reference), when the admin runs a subject access request for the producer's user id (resolved to the per-tenant pseudonymous id, not stored or logged raw), then an export of all stored data linked to that pseudonymous id across all tenants is generated within 15 minutes [proposed, Q-37] in a machine-readable format [JSON proposed, Q-37], contains no other subject's data, is downloadable only by the requesting admin through the admin screen, and expires and is deleted automatically after 7 days [proposed, Q-37]; each download is audited.
- AC-11.2: Given a verified erasure request, when the admin executes it, then 0 records linked to the subject's pseudonymous ids remain in the event store, the dead-letter store and the messaging layer, and derived aggregates are recomputed so that totals and unique-user counts equal a recount from the remaining stored events (tolerance 0), verified by queries on each store (confirmed, CR-001).
- AC-11.3: Given a subject access or erasure run, when it completes, then an audit entry records the request id, admin id, verification reference, time and counts, without the raw user id or other raw identifier.
- AC-11.4: Given a request for which no data is linked to the subject, when the admin runs it, then the screen states that no data is held, and an audit entry records the request and outcome.
- AC-11.5: Given an executed erasure, when 35 days have passed, then every backup older than the erasure contains no data of the subject or has been replaced by backups purged of it, and the deletion ledger holds an entry for the erasure without any identifying data (confirmed, CR-001).

### US-12 (P-3, REQ-14, REQ-17, REQ-30)

As a platform admin, I want to set retention per tenant in the admin screen, so that data is not kept longer than allowed.

- AC-12.1: Given a tenant with retention of N days (default 396 days = 13 months), when the purge job runs (at least daily [confirmed, Q-23]), then events whose ingest time is older than N days are not returned by any query and are physically removed within 24 hours [confirmed, Q-23] of the purge run, and from backups within 35 days [confirmed].
- AC-12.2: Given an admin changes a tenant's retention in the admin screen, when saved, then an audit entry is written and the change applies to existing data at the next purge run; shortening is applied, and lengthening never resurrects purged data, including after a restore.
- AC-12.3: Given an admin enters a retention value that is missing, non-numeric, fractional, zero, negative, below 1 day or above 396 days, when saved, then it is rejected with a field-level validation message and the existing value is unchanged; 1 and 396 are accepted (CR-017).
- AC-12.4: Given a restore from backup after erasures and purges, when the restore finishes, then before any query is served the deletion ledger and retention purge are re-applied, and a verification query finds 0 records of erased subjects and 0 events past retention (confirmed, CR-001).
- AC-12.5: Given an admin shortens a tenant's retention such that data would be destroyed, when they save, then a confirmation step states how much data will be purged and nothing is purged until confirmed [proposed, Q-40].

### US-13 (P-4, P-1, REQ-16, REQ-19, REQ-23)

As a data subject, I want raw personal data never kept beyond defined bounds and my user id only kept as a pseudonym, so that my privacy is protected.

- AC-13.2: Given the event contract, when it is reviewed, then it contains no consent field, and the platform performs no consent lookup or recording; stripping applies identically to every event.
- AC-13.3: Given an event with free-form properties, when it is received, then only properties whose keys are on the tenant's allow-list are stored, unlisted keys are dropped, and a dropped-key count per tenant is recorded without the dropped values.
- AC-13.4: Given the same producer user id in tenant A on two events, when stored, then both carry the identical pseudonymous id; and given the same user id in tenant B, then the pseudonymous id differs from tenant A's; and the raw user id appears in no store.
- AC-13.5: Given an event with an IP address, a user agent and a device id, when stored, then the stored record has country (derived from the IP) and browser/OS family only, and contains no raw IP, truncated IP, precise location, raw or hashed device id, or raw user agent (confirmed, CR-004, CR-010, CR-011).
- AC-13.6: Given raw events in the messaging layer, when 24 hours have passed since the intake step acknowledged them, then they are no longer present in the messaging layer, and its storage and backups are encrypted at rest (confirmed, CR-002).
- AC-13.7: Given an event with an allowed key whose value contains an email address or phone number, or exceeds the bounded length (256 characters [proposed, Q-34]) or declared type, when it is received, then the value is not stored, the event is otherwise stored or dead-lettered per the contract, and a counter records the detection without the value (CR-011).
- AC-13.8: Given a new application needing a new free-form property key, when an admin adds the key to that tenant's allow-list in the admin screen [proposed, Q-34], then the key is accepted from that tenant with no service code change, rebuild or contract release (CR-011).
- AC-13.9: Given the staging-like environment, when its configuration and storage are inspected, then the event store, the messaging layer and all backups are encrypted at rest (NFR-12).

### US-15 (P-1, REQ-6, REQ-7, REQ-28)

As a producer-app developer, I want invalid events rejected visibly and duplicates ignored, so that data quality is trustworthy.

- AC-15.1: Given an authenticated producer sends an event that violates the schema (missing required field, wrong type, unknown event type or unsupported version), when it is received, then it is not stored as valid data, it is dead-lettered with a reason code and the offending field path, and a rejection counter for the tenant increments.
- AC-15.2: Given the same event id delivered 3 times in one tenant within the deduplication window, when processed, then exactly 1 record is stored and counts in the dashboard increase by 1.
- AC-15.3: Given an event whose event time is more than 7 days before ingest or more than 5 minutes after ingest [proposed, Q-33], when received, then it is dead-lettered with reason "timestamp_out_of_bounds"; and an event within bounds that arrives late is stored under its event time (CR-008).
- AC-15.4: Given an authenticated producer that sends invalid messages continuously, when its dead-letter share reaches 10,000 messages per credential or 100,000 per tenant [proposed, Q-31], then further invalid messages from it are counted and discarded without storage, valid events keep flowing, other credentials' and tenants' dead-letter storage is unaffected, and an audit entry records the first discard (CR-003).

- AC-15.6: Given a dead-lettered event is replayed and an event with the same (tenant, event id) is already stored, when processed, then no second record is stored (CR-007).
- AC-15.7: Given an event deleted by erasure, purge or retention, when the same event is redelivered within the deduplication window or the messaging-layer retention, then it is not stored again (CR-007).
- AC-15.8: Given an event larger than 64 KB, or a malformed message that would crash a consumer, when received, then it is dead-lettered with a reason code, consumer processes keep running, and other messages continue with no interruption (CR-018).

- Production hosting, production availability targets (Deferred, PO, 2026-10-21) and data residency (Deferred, PO, 2026-10-21).
- Billing, external customers, third-party data sharing.
- Dashboard alerting (threshold notifications to users), funnels, cohorts, custom report builder, and data export from the dashboard (confirmed out of scope, Q-11). Operational alert-readiness of platform metrics (NFR-19) is in scope; alert delivery is not specified for v1 (CR-019). GDPR subject access export (REQ-18) is in scope.
- Data-subject rectification, restriction and objection (GDPR Arts. 16, 18, 21): out of scope for v1 (proposed, Q-38). Access (Art. 15) and erasure (Art. 17) are in scope.
- Per-user views in the dashboard (Q-25).
- Email sending of any kind in v1 (Q-27).
- Recording or processing of user consent (Q-5).
- Mobile or native dashboard clients; A/B testing; real-time (sub-second) streaming dashboards.
- Naming of specific real applications as sample producers (Deferred, PO, 2026-10-21; Q-10b).
